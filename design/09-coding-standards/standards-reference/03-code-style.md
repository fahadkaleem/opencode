## 1. Overview

### 1.1 Purpose

This document establishes mandatory code style and formatting rules for
TypeScript/Node.js projects. These rules ensure consistent, readable code that
can be reliably generated by AI agents and maintained by human developers.

### 1.2 Scope

**Applies to**:

- All TypeScript source files (`.ts`, `.tsx`)
- JavaScript configuration files (`.js`, `.mjs`)
- JSON configuration files
- Markdown documentation

**Does NOT apply to**:

- Generated files in `dist/`, `bundle/`, `node_modules/`
- Third-party code and vendored dependencies
- Build artifacts

### 1.3 Enforcement Level

| Level      | Meaning                                     | Mechanism                   |
| ---------- | ------------------------------------------- | --------------------------- |
| **MUST**   | Mandatory; violations block merge           | ESLint error, Prettier, CI  |
| **SHOULD** | Strongly recommended; exceptions documented | ESLint warning, code review |
| **MAY**    | Optional; team preference                   | Documentation only          |

---

## 2. Guiding Principles

| Principle                  | Description                                                 |
| -------------------------- | ----------------------------------------------------------- |
| Consistency First          | Identical patterns across entire codebase; no style debates |
| Automation Over Convention | Rules enforced by tooling, not memorization                 |
| Readability                | Code reads naturally; minimize cognitive load               |
| Explicit Over Implicit     | Clear intent; no hidden behaviors                           |

## 3. Rules

### 3.1 Imports

#### Rule 3.1.1: Import Order

| Attribute       | Value                          |
| --------------- | ------------------------------ |
| **Enforcement** | MUST                           |
| **Automation**  | ESLint `import/order` + Manual |
| **Applies to**  | All TypeScript files           |

**Rule Statement**: Imports SHALL be organized in groups, separated by blank
lines, in the following order:

1. Node.js built-ins (with `node:` protocol)
2. External packages (npm dependencies)
3. Internal package imports (relative paths)

**Correct Examples**:

```typescript
// CORRECT: Proper import grouping and ordering
import * as fs from 'node:fs/promises';
import * as path from 'node:path';

import { z } from 'zod';
import { simpleGit } from 'simple-git';

import { Config } from '../config/config.js';
import { isNodeError } from '../utils/errors.js';
import type { Storage } from '../config/storage.js';
```

**Incorrect Examples**:

```typescript
// INCORRECT: Mixed import groups, no separation
import { Config } from '../config/config.js';
import * as fs from 'node:fs/promises';
import { z } from 'zod';
import * as path from 'node:path';
```

```typescript
// INCORRECT: Missing node: protocol for built-ins
import * as fs from 'fs/promises';
import * as path from 'path';
```

**Rationale**: Consistent import ordering makes it easy to scan dependencies and
identify import sources.

---

#### Rule 3.1.2: Node.js Protocol Required

| Attribute       | Value                                       |
| --------------- | ------------------------------------------- |
| **Enforcement** | MUST                                        |
| **Automation**  | ESLint `import/enforce-node-protocol-usage` |
| **Applies to**  | All Node.js built-in imports                |

**Rule Statement**: Node.js built-in modules SHALL use the `node:` protocol
prefix so that built-ins are clearly distinguished from npm packages.

**Correct Examples**:

```typescript
// CORRECT: node: protocol for built-ins
import * as fs from 'node:fs/promises';
import * as path from 'node:path';
import { EOL } from 'node:os';
import * as crypto from 'node:crypto';
```

**Incorrect Examples**:

```typescript
// INCORRECT: Missing node: protocol
import * as fs from 'fs/promises';
import * as path from 'path';
import { EOL } from 'os';
```

**Rationale**: The `node:` protocol explicitly identifies Node.js built-ins,
preventing confusion with npm packages of similar names.

---

#### Rule 3.1.3: File Extension Required

| Attribute       | Value                                     |
| --------------- | ----------------------------------------- |
| **Enforcement** | MUST                                      |
| **Automation**  | TypeScript `moduleResolution: "nodenext"` |
| **Applies to**  | All relative imports                      |

**Rule Statement**: Relative imports SHALL include the `.js` file extension
(even for TypeScript files) so that ESM resolution works correctly.

**Correct Examples**:

```typescript
// CORRECT: .js extension on relative imports
import { Config } from '../config/config.js';
import { isNodeError } from '../utils/errors.js';
import type { Storage } from '../config/storage.js';
```

**Incorrect Examples**:

```typescript
// INCORRECT: Missing file extension
import { Config } from '../config/config';
import { isNodeError } from '../utils/errors';
```

```typescript
// INCORRECT: Using .ts extension
import { Config } from '../config/config.ts';
```

**Rationale**: ESM requires explicit file extensions. TypeScript compiles `.ts`
to `.js`, so imports must reference the output extension.

---

#### Rule 3.1.4: Type-Only Imports

| Attribute       | Value                                               |
| --------------- | --------------------------------------------------- |
| **Enforcement** | MUST                                                |
| **Automation**  | ESLint `@typescript-eslint/consistent-type-imports` |
| **Applies to**  | All type-only imports                               |

**Rule Statement**: Imports used only as types SHALL use the `type` keyword so
that they are removed during compilation and prevent runtime errors.

**Correct Examples**:

```typescript
// CORRECT: type keyword for type-only imports
import type { Config } from '../config/config.js';
import type { SimpleGit } from 'simple-git';
import { simpleGit, CheckRepoActions } from 'simple-git';

// CORRECT: Inline type imports in mixed import
import { isNodeError, type NodeError } from '../utils/errors.js';
```

**Incorrect Examples**:

```typescript
// INCORRECT: Missing type keyword for type-only import
import { Config } from '../config/config.js'; // If Config is only used as a type

// INCORRECT: Importing type and value together without type keyword
import { SimpleGit, simpleGit } from 'simple-git'; // If SimpleGit is only used as type
```

**Rationale**: Type-only imports are erased at compile time, reducing bundle
size and preventing runtime import errors for type-only modules.

---

#### Rule 3.1.5: Named Exports Preferred

| Attribute       | Value                                       |
| --------------- | ------------------------------------------- |
| **Enforcement** | SHOULD                                      |
| **Automation**  | ESLint `import/no-default-export` (warning) |
| **Applies to**  | All exports                                 |

**Rule Statement**: Modules SHOULD use named exports instead of default exports
so that imports are consistent and refactoring is safer.

**Correct Examples**:

```typescript
// CORRECT: Named exports
export class UserService {}
export function createUser() {}
export const MAX_RETRIES = 3;

// CORRECT: Re-exporting from barrel file
export { UserService } from './userService.js';
export { createUser, MAX_RETRIES } from './utils.js';
```

**Incorrect Examples**:

```typescript
// INCORRECT: Default export
export default class UserService {}

// INCORRECT: Default export function
export default function createUser() {}
```

**Exception**: Default exports are allowed for CLI command files when required
by the framework (e.g., oclif).

**Rationale**: Named exports enable better IDE auto-completion, prevent naming
mismatches, and make refactoring safer.

---

#### Rule 3.1.6: No require() Calls

| Attribute       | Value                         |
| --------------- | ----------------------------- |
| **Enforcement** | MUST                          |
| **Automation**  | ESLint `no-restricted-syntax` |
| **Applies to**  | All source files              |

**Rule Statement**: All imports SHALL use ES6 `import` syntax; CommonJS
`require()` is forbidden so that the codebase uses a single module system.

**Correct Examples**:

```typescript
// CORRECT: ES6 import
import * as fs from 'node:fs/promises';
import { glob } from 'glob';
```

**Incorrect Examples**:

```typescript
// INCORRECT: CommonJS require
const fs = require('fs');
const { glob } = require('glob');
```

**Rationale**: ES modules are the standard for modern JavaScript/TypeScript.
Mixing module systems causes confusion and compatibility issues.

### 3.3 Formatting

#### Rule 3.3.1: Indentation

| Attribute       | Value                  |
| --------------- | ---------------------- |
| **Enforcement** | MUST                   |
| **Automation**  | Prettier, EditorConfig |
| **Applies to**  | All source files       |

**Rule Statement**: Code SHALL use 2 spaces for indentation; tabs are forbidden
(except in Makefiles).

**Correct Examples**:

```typescript
// CORRECT: 2-space indentation
export class UserService {
  private readonly repository: UserRepository;

  constructor(repository: UserRepository) {
    this.repository = repository;
  }

  async findUser(id: string): Promise<User | null> {
    if (!id) {
      return null;
    }
    return this.repository.findById(id);
  }
}
```

**Incorrect Examples**:

```typescript
// INCORRECT: 4-space indentation
export class UserService {
  private readonly repository: UserRepository;

  constructor(repository: UserRepository) {
    this.repository = repository;
  }
}
```

```typescript
// INCORRECT: Tab indentation
export class UserService {
→ private readonly repository: UserRepository;
}
```

**Rationale**: 2-space indentation is the TypeScript/JavaScript community
standard and keeps code compact.

---

#### Rule 3.3.2: Line Length

| Attribute       | Value                     |
| --------------- | ------------------------- |
| **Enforcement** | MUST                      |
| **Automation**  | Prettier `printWidth: 80` |
| **Applies to**  | All source files          |

**Rule Statement**: Lines SHALL NOT exceed 80 characters so that code is
readable on split screens and in code review tools.

**Correct Examples**:

```typescript
// CORRECT: Line broken at 80 characters
const errorMessage = `Failed to initialize checkpointing: ${
  error instanceof Error ? error.message : 'Unknown error'
}. Please check that Git is working properly.`;

// CORRECT: Method chain broken across lines
const result = await this.shadowGitRepository.raw(['restore', '--source', commitHash, '.']);
```

**Incorrect Examples**:

```typescript
// INCORRECT: Line exceeds 80 characters
const errorMessage = `Failed to initialize checkpointing: ${error instanceof Error ? error.message : 'Unknown error'}. Please check that Git is working properly or disable checkpointing.`;
```

**Rationale**: 80-character lines improve readability, especially in
side-by-side diffs and split-screen editors.

---

#### Rule 3.3.3: Semicolons Required

| Attribute       | Value                 |
| --------------- | --------------------- |
| **Enforcement** | MUST                  |
| **Automation**  | Prettier `semi: true` |
| **Applies to**  | All statements        |

**Rule Statement**: All statements SHALL end with a semicolon so that automatic
semicolon insertion (ASI) issues are avoided.

**Correct Examples**:

```typescript
// CORRECT: Semicolons on all statements
const name = 'example';
const items = [1, 2, 3];
console.log(name);
```

**Incorrect Examples**:

```typescript
// INCORRECT: Missing semicolons
const name = 'example';
const items = [1, 2, 3];
console.log(name);
```

**Rationale**: Explicit semicolons prevent subtle bugs caused by JavaScript's
automatic semicolon insertion.

---

#### Rule 3.3.4: Quote Style

| Attribute       | Value                        |
| --------------- | ---------------------------- |
| **Enforcement** | MUST                         |
| **Automation**  | Prettier `singleQuote: true` |
| **Applies to**  | All string literals          |

**Rule Statement**: String literals SHALL use single quotes; double quotes are
reserved for JSX attributes and strings containing single quotes.

**Correct Examples**:

```typescript
// CORRECT: Single quotes for strings
const name = 'example';
const message = 'Hello, world!';

// CORRECT: Double quotes when string contains single quote
const greeting = "It's a beautiful day";

// CORRECT: Template literals for interpolation
const fullName = `${firstName} ${lastName}`;

// CORRECT: Double quotes in JSX attributes
<Button label="Click me" />
```

**Incorrect Examples**:

```typescript
// INCORRECT: Double quotes for regular strings
const name = 'example';
const message = 'Hello, world!';
```

**Rationale**: Single quotes are the dominant convention in
TypeScript/JavaScript and reduce visual noise.

---

#### Rule 3.3.5: Trailing Commas

| Attribute       | Value                                  |
| --------------- | -------------------------------------- |
| **Enforcement** | MUST                                   |
| **Automation**  | Prettier `trailingComma: "all"`        |
| **Applies to**  | Multi-line arrays, objects, parameters |

**Rule Statement**: Multi-line arrays, objects, and parameter lists SHALL
include trailing commas so that diffs are cleaner when adding new items.

**Correct Examples**:

```typescript
// CORRECT: Trailing commas in multi-line structures
const config = {
  name: 'example',
  version: '1.0.0',
  enabled: true,
};

const items = ['first', 'second', 'third'];

function example(param1: string, param2: number, param3: boolean) {
  // ...
}
```

**Incorrect Examples**:

```typescript
// INCORRECT: Missing trailing commas
const config = {
  name: 'example',
  version: '1.0.0',
  enabled: true,
};

const items = ['first', 'second', 'third'];
```

**Rationale**: Trailing commas produce cleaner git diffs when adding new items
and prevent missing comma errors.

---

#### Rule 3.3.6: Line Endings

| Attribute       | Value             |
| --------------- | ----------------- |
| **Enforcement** | MUST              |
| **Automation**  | EditorConfig, Git |
| **Applies to**  | All files         |

**Rule Statement**: All files SHALL use LF (Unix-style) line endings, never
CRLF.

**Configuration**:

```ini
# .editorconfig
[*]
end_of_line = lf
```

```ini
# .gitattributes
* text=auto eol=lf
```

**Rationale**: Consistent line endings prevent spurious diffs and cross-platform
issues.

---

#### Rule 3.3.7: Final Newline

| Attribute       | Value        |
| --------------- | ------------ |
| **Enforcement** | MUST         |
| **Automation**  | EditorConfig |
| **Applies to**  | All files    |

**Rule Statement**: All files SHALL end with a single newline character.

**Rationale**: POSIX standard for text files; prevents issues with some tools
and cleaner diffs.

### 3.4 Syntax Style

#### Rule 3.4.1: Variable Declarations

| Attribute       | Value                                      |
| --------------- | ------------------------------------------ |
| **Enforcement** | MUST                                       |
| **Automation**  | ESLint `no-var`, `prefer-const`, `one-var` |
| **Applies to**  | All variable declarations                  |

**Rule Statement**: Variables SHALL be declared using `const` by default; `let`
is allowed only when reassignment is needed; `var` is forbidden.

**Correct Examples**:

```typescript
// CORRECT: const for values that don't change
const userName = 'Alice';
const config = { timeout: 5000 };
const items = [1, 2, 3];

// CORRECT: let only when reassignment is needed
let retryCount = 0;
retryCount += 1;

// CORRECT: One declaration per statement
const firstName = 'John';
const lastName = 'Doe';
```

**Incorrect Examples**:

```typescript
// INCORRECT: var is forbidden
var userName = 'Alice';

// INCORRECT: let when const would work
let config = { timeout: 5000 }; // Never reassigned

// INCORRECT: Multiple declarations in one statement
const firstName = 'John',
  lastName = 'Doe';
```

**Rationale**: `const` signals immutability, preventing accidental reassignment.
`var` has confusing hoisting behavior.

---

#### Rule 3.4.2: Equality Operators

| Attribute       | Value                    |
| --------------- | ------------------------ |
| **Enforcement** | MUST                     |
| **Automation**  | ESLint `eqeqeq`          |
| **Applies to**  | All equality comparisons |

**Rule Statement**: Comparisons SHALL use strict equality (`===`, `!==`); loose
equality (`==`, `!=`) is forbidden except for null checks.

**Correct Examples**:

```typescript
// CORRECT: Strict equality
if (status === 'active') {
}
if (count !== 0) {
}
if (user.id === targetId) {
}

// CORRECT: null check with loose equality (allowed exception)
if (value == null) {
} // Checks both null and undefined
```

**Incorrect Examples**:

```typescript
// INCORRECT: Loose equality
if (status == 'active') {
}
if (count != 0) {
}
```

**Rationale**: Strict equality prevents type coercion bugs. The null exception
is idiomatic for checking null/undefined.

---

#### Rule 3.4.3: Arrow Functions

| Attribute       | Value                                              |
| --------------- | -------------------------------------------------- |
| **Enforcement** | MUST                                               |
| **Automation**  | ESLint `prefer-arrow-callback`, `arrow-body-style` |
| **Applies to**  | Callback functions and simple expressions          |

**Rule Statement**: Callback functions SHALL use arrow function syntax. Arrow
functions SHALL omit braces and `return` when the body is a single expression.

**Correct Examples**:

```typescript
// CORRECT: Arrow function for callbacks
items.forEach((item) => {
  processItem(item);
});

// CORRECT: Implicit return for single expressions
const doubled = items.map((n) => n * 2);
const names = users.map((u) => u.name);

// CORRECT: Braces when body has multiple statements
const processed = items.filter((item) => {
  if (item.skip) return false;
  return item.value > 0;
});
```

**Incorrect Examples**:

```typescript
// INCORRECT: function keyword for callbacks
items.forEach(function (item) {
  processItem(item);
});

// INCORRECT: Unnecessary braces and return
const doubled = items.map((n) => {
  return n * 2;
});
```

**Rationale**: Arrow functions are more concise and don't rebind `this`.
Implicit returns reduce boilerplate.

---

#### Rule 3.4.4: Object Shorthand

| Attribute       | Value                     |
| --------------- | ------------------------- |
| **Enforcement** | MUST                      |
| **Automation**  | ESLint `object-shorthand` |
| **Applies to**  | Object literals           |

**Rule Statement**: Object literals SHALL use shorthand syntax for properties
and methods when variable names match property names.

**Correct Examples**:

```typescript
// CORRECT: Property shorthand
const name = 'Alice';
const age = 30;
const user = { name, age };

// CORRECT: Method shorthand
const service = {
  async fetchData() {
    return await api.get('/data');
  },
  processResult(data) {
    return transform(data);
  },
};
```

**Incorrect Examples**:

```typescript
// INCORRECT: Redundant property names
const user = { name: name, age: age };

// INCORRECT: Verbose method syntax
const service = {
  fetchData: async function () {
    return await api.get('/data');
  },
  processResult: function (data) {
    return transform(data);
  },
};
```

**Rationale**: Shorthand syntax reduces duplication and improves readability.

---

#### Rule 3.4.5: Curly Braces

| Attribute       | Value                        |
| --------------- | ---------------------------- |
| **Enforcement** | MUST                         |
| **Automation**  | ESLint `curly: "multi-line"` |
| **Applies to**  | Control flow statements      |

**Rule Statement**: Control flow statements SHALL use curly braces when the body
spans multiple lines. Single-line bodies MAY omit braces.

**Correct Examples**:

```typescript
// CORRECT: Single-line without braces
if (!user) return null;
if (isEmpty) throw new Error('Empty');

// CORRECT: Multi-line with braces
if (!user) {
  logger.warn('User not found');
  return null;
}

// CORRECT: Braces for clarity in complex conditions
if (isValid && hasPermission) {
  performAction();
}
```

**Incorrect Examples**:

```typescript
// INCORRECT: Multi-line without braces
if (!user) logger.warn('User not found');
return null; // This always executes!

// INCORRECT: Inconsistent bracing in if/else
if (condition) doSomething();
else {
  doSomethingElse();
  logAction();
}
```

**Rationale**: Multi-line bodies require braces to prevent bugs from indentation
confusion.

---

#### Rule 3.4.6: Unused Variables

| Attribute       | Value                                      |
| --------------- | ------------------------------------------ |
| **Enforcement** | MUST                                       |
| **Automation**  | ESLint `@typescript-eslint/no-unused-vars` |
| **Applies to**  | All variables, parameters, imports         |

**Rule Statement**: Unused variables SHALL be removed. Intentionally unused
parameters SHALL be prefixed with underscore (`_`).

**Correct Examples**:

```typescript
// CORRECT: Unused parameter prefixed with underscore
async function handleError(_error: Error): Promise<void> {
  // Error intentionally not used
  return;
}

// CORRECT: Unused destructured values
const { used, _unused } = getValues();

// CORRECT: Unused catch variable
try {
  await riskyOperation();
} catch (_error) {
  return fallbackValue;
}
```

**Incorrect Examples**:

```typescript
// INCORRECT: Unused variable without underscore prefix
const unused = getValue(); // Never used

// INCORRECT: Unused parameter without underscore
function handleClick(event: Event): void {
  // event never used
  doSomething();
}
```

**Rationale**: Unused code is dead weight. The underscore convention signals
intentional omission.

---

#### Rule 3.4.7: Type Assertions

| Attribute       | Value                                                  |
| --------------- | ------------------------------------------------------ |
| **Enforcement** | MUST                                                   |
| **Automation**  | ESLint `@typescript-eslint/consistent-type-assertions` |
| **Applies to**  | All type assertions                                    |

**Rule Statement**: Type assertions SHALL use `as` syntax; angle-bracket syntax
is forbidden.

**Correct Examples**:

```typescript
// CORRECT: as syntax
const element = document.getElementById('app') as HTMLElement;
const config = JSON.parse(data) as Config;
```

**Incorrect Examples**:

```typescript
// INCORRECT: Angle-bracket syntax
const element = <HTMLElement>document.getElementById('app');
const config = <Config>JSON.parse(data);
```

**Rationale**: The `as` syntax is required in JSX files and provides consistency
across the codebase.

---

#### Rule 3.4.8: Explicit any Forbidden

| Attribute       | Value                                       |
| --------------- | ------------------------------------------- |
| **Enforcement** | MUST                                        |
| **Automation**  | ESLint `@typescript-eslint/no-explicit-any` |
| **Applies to**  | All type annotations                        |

**Rule Statement**: The `any` type is forbidden. Use `unknown` for truly unknown
types, then narrow with type guards.

**Correct Examples**:

```typescript
// CORRECT: unknown with type narrowing
function processValue(value: unknown): string {
  if (typeof value === 'string') {
    return value;
  }
  if (typeof value === 'number') {
    return String(value);
  }
  throw new Error('Unsupported type');
}

// CORRECT: Specific type instead of any
function handleResponse(response: ApiResponse): void {
  // ...
}
```

**Incorrect Examples**:

```typescript
// INCORRECT: Explicit any
function processValue(value: any): string {
  return value.toString();
}

// INCORRECT: any in generics
function wrap<T = any>(value: T): Wrapper<T> {
  return { value };
}
```

**Exception**: Test files may use `any` when mocking complex types, but must
include eslint-disable comment.

**Rationale**: `any` disables type checking and defeats TypeScript's purpose.
`unknown` is type-safe.

---

#### Rule 3.4.9: Member Accessibility

| Attribute       | Value                                                     |
| --------------- | --------------------------------------------------------- |
| **Enforcement** | MUST                                                      |
| **Automation**  | ESLint `@typescript-eslint/explicit-member-accessibility` |
| **Applies to**  | Class members                                             |

**Rule Statement**: Class members SHALL NOT have explicit `public` modifier;
public is the default. Private and protected modifiers are required when
applicable.

**Correct Examples**:

```typescript
// CORRECT: No public modifier, explicit private
class UserService {
  private readonly repository: UserRepository;

  constructor(repository: UserRepository) {
    this.repository = repository;
  }

  async findUser(id: string): Promise<User | null> {
    return this.repository.findById(id);
  }

  private validateId(id: string): boolean {
    return id.length > 0;
  }
}
```

**Incorrect Examples**:

```typescript
// INCORRECT: Explicit public modifier
class UserService {
  public async findUser(id: string): Promise<User | null> {
    return this.repository.findById(id);
  }
}
```

**Rationale**: Explicit `public` is redundant noise since it's the default.
Private/protected provide meaningful information.

---

#### Rule 3.4.10: Switch Default Case

| Attribute       | Value                 |
| --------------- | --------------------- |
| **Enforcement** | MUST                  |
| **Automation**  | ESLint `default-case` |
| **Applies to**  | All switch statements |

**Rule Statement**: Switch statements SHALL include a `default` case, even if
empty with a comment explaining why.

**Correct Examples**:

```typescript
// CORRECT: Default case with action
switch (status) {
  case 'pending':
    return processPending();
  case 'complete':
    return processComplete();
  default:
    throw new Error(`Unknown status: ${status}`);
}

// CORRECT: Exhaustive switch with never check
switch (status) {
  case 'pending':
    return processPending();
  case 'complete':
    return processComplete();
  default: {
    const _exhaustive: never = status;
    throw new Error(`Unhandled status: ${status}`);
  }
}
```

**Incorrect Examples**:

```typescript
// INCORRECT: Missing default case
switch (status) {
  case 'pending':
    return processPending();
  case 'complete':
    return processComplete();
}
```

**Rationale**: Default cases catch unexpected values and make switch statements
explicit about all possibilities.

---

#### Rule 3.4.11: Throwing Errors

| Attribute       | Value                         |
| --------------- | ----------------------------- |
| **Enforcement** | MUST                          |
| **Automation**  | ESLint `no-restricted-syntax` |
| **Applies to**  | All throw statements          |

**Rule Statement**: Only Error objects (or subclasses) SHALL be thrown; throwing
string literals is forbidden.

**Correct Examples**:

```typescript
// CORRECT: Throwing Error objects
throw new Error('Operation failed');
throw new ValidationError('Invalid input');
throw new NotFoundError(`User ${id} not found`);
```

**Incorrect Examples**:

```typescript
// INCORRECT: Throwing string literals
throw 'Operation failed';
throw `User ${id} not found`;
```

**Rationale**: Error objects provide stack traces and can be caught by type.
String throws lose debugging information.

### 3.5 Array Type Syntax

#### Rule 3.5.1: Array Type Notation

| Attribute       | Value                                  |
| --------------- | -------------------------------------- |
| **Enforcement** | MUST                                   |
| **Automation**  | ESLint `@typescript-eslint/array-type` |
| **Applies to**  | All array type annotations             |

**Rule Statement**: Simple array types SHALL use `T[]` syntax. Complex types
(unions, intersections) SHALL use `Array<T>` syntax.

**Correct Examples**:

```typescript
// CORRECT: Simple types use T[]
const numbers: number[] = [1, 2, 3];
const users: User[] = [];
const names: string[] = ['Alice', 'Bob'];

// CORRECT: Complex types use Array<T>
const mixed: Array<string | number> = [1, 'two', 3];
const nested: Array<Map<string, number>> = [];
```

**Incorrect Examples**:

```typescript
// INCORRECT: Array<T> for simple types
const numbers: Array<number> = [1, 2, 3];
const users: Array<User> = [];

// INCORRECT: T[] for complex types
const mixed: (string | number)[] = [1, 'two', 3];
```

**Rationale**: `T[]` is more readable for simple types. `Array<T>` is clearer
when T is complex.

## 5. Anti-Patterns

### 5.1 Forbidden Patterns

| Pattern                  | Why Forbidden                  | Correct Alternative      | Severity      |
| ------------------------ | ------------------------------ | ------------------------ | ------------- |
| `var` keyword            | Hoisting bugs, confusing scope | `const` or `let`         | Critical      |
| `require()`              | Mixed module systems           | ES6 `import`             | Critical      |
| `==` / `!=`              | Type coercion bugs             | `===` / `!==`            | High          |
| `any` type               | Disables type safety           | `unknown` with narrowing | High          |
| Angle-bracket assertions | JSX conflicts                  | `as` syntax              | Medium        |
| Throwing strings         | No stack trace                 | `throw new Error()`      | High          |
| Default exports          | Naming inconsistency           | Named exports            | Low (warning) |

### 5.2 Common Violations

```typescript
// VIOLATION: Mixed import styles
var fs = require('fs');
import { z } from 'zod';

// FIX: All ES6 imports
import * as fs from 'node:fs/promises';
import { z } from 'zod';
```

```typescript
// VIOLATION: Unnecessary explicit any
function parse(data: any): Config {
  return data as Config;
}

// FIX: Use unknown with validation
function parse(data: unknown): Config {
  if (!isConfig(data)) {
    throw new Error('Invalid config');
  }
  return data;
}
```

## 6. Decision Flowcharts

### 6.1 Choosing const vs let

```
When declaring a variable:
├─ Will the value be reassigned?
│   ├─ Yes → Use let
│   └─ No → Use const
└─ Never use var
```

### 6.2 Import Style Decision

```
When importing:
├─ Is it a Node.js built-in?
│   └─ Yes → Use node: protocol (import * as fs from 'node:fs')
├─ Is it only used as a type?
│   └─ Yes → Use type keyword (import type { X } from './x.js')
├─ Is it a relative import?
│   └─ Yes → Include .js extension
└─ Group and order: built-ins → external → internal
```

### 6.3 Array Type Syntax Decision

```
When typing an array:
├─ Is the element type simple (single type name)?
│   └─ Yes → Use T[] syntax (string[], User[])
└─ Is it complex (union, intersection, generic)?
    └─ Yes → Use Array<T> syntax (Array<string | number>)
```

## 9. Quick Reference

### 9.1 Most Common Rules

1. **Use `const` by default**: Only use `let` when reassignment is needed
2. **Single quotes**: Use `'string'` not `"string"`
3. **`node:` protocol**: `import * as fs from 'node:fs'`
4. **`.js` extension**: `import { x } from './module.js'`
5. **Type imports**: `import type { X }` for types only
6. **Underscore unused**: `_unusedParam` for intentional unused

### 9.2 Cheat Sheet

```
Imports:
  node:* first    → import * as fs from 'node:fs/promises'
  External second → import { z } from 'zod'
  Internal third  → import { Config } from './config.js'
  Types use type  → import type { User } from './types.js'

Variables:
  Default         → const x = value
  Reassigned      → let count = 0
  Forbidden       → var (never use)
  Unused          → _unused prefix

Syntax:
  Quotes          → 'single quotes'
  Semicolons      → required;
  Trailing commas → { a, b, }
  Equality        → === and !==
  Assertions      → value as Type
```
